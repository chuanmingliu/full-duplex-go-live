## Backend token-budget failure

A replay of the saved prompt and conversation prefix around the caller's
operation question reproduced a failed backend response. With the provider's
default reasoning setting, two further requests stopped at `max_output_tokens`:

| Setting | Request duration | Outcome |
| --- | ---: | --- |
| Provider default | 5858 ms | HTTP 500 |
| No reasoning | 2946 ms | Complete answer |
| Provider default | 6093 ms | 245 reasoning tokens, 11 output tokens; incomplete |
| No reasoning | 5237 ms | Complete answer, 60 output tokens |
| Provider default | 4718 ms | 220 reasoning tokens, 36 output tokens; incomplete |
| No reasoning | 3236 ms | Complete answer, 49 output tokens |

The same model (`gpt-6-luna`), prompt, conversation and 256-token cap were used;
requests were sequential and caching varied. This is a small backend-only
comparison, not an end-to-end speed guarantee. It demonstrates why accepting
truncated output would be wrong and why merely increasing the output cap could
spend more time reasoning. [Speko documents](https://docs.speko.ai/relay/llm/responses)
that this cap includes hidden reasoning and supports `reasoning_effort: none`.

The client backend now defaults to `none`, preserves rejection of incomplete
answers, and logs request duration and success without transcript content.
`SPEKO_RESPONSES_REASONING=provider_default` restores omission of the field.
This fixes the reproduced token-budget problem; business tools remain absent,
so it does not enable real quotations, external lookups, transfers, or purchases.

## Call termination

The caller and assistant exchanged farewells, but the old bridge never issued
an assistant-hangup control. The new opt-in `SPEKO_AUTO_HANGUP=1` recognizes only
a small set of complete, reciprocal farewell phrases. It waits for transcript
settling and voiced playback to drain before sending normal WebSocket close
code 1000 with `assistant_hangup`, which the deployed SIP adapter translates
into BYE. New caller speech or text cancels the pending close. Quotes, questions,
negation, ambiguous requests and arbitrary farewell sentences do not match.
This is a conservative local policy, not a general semantic end-call tool.

Separately, RustPBX `0.5.0-rc.1-d899595-community` recorded the carrier BYE and
callee hangup at 15:04:45.258 UTC. The adapter remained connected until controlled
cleanup at 15:05:24.394 UTC, approximately 39 seconds later. Its final failure
status records that cleanup signal. The application's own cleanup BYE received
an acknowledgment. Historical logs do not establish whether the earlier remote
BYE was routed incorrectly, dropped, or rejected. SIP source validation is
unchanged; this separate propagation fault is not declared fixed.

## Verification boundary

Targeted tests cover fragmented reciprocal farewells, incomplete/ambiguous
phrases, caller continuation, queued audio, and normal close classification.
An integrated local test runs the real bridge and SIP adapter against a mock
voice provider and SIP peer, receives all farewell RTP frames, and acknowledges
the resulting BYE. These tests do not replace a real handset check.


A no-phone live-provider probe (`goodbye-3aa5c7c1c6d0`) replayed the recorded
final caller farewell after a short greeting and a narrow Chinese test prompt.
It received the matching assistant farewell and normal `assistant_hangup`
close at 10.143 seconds. This verifies the live event path for that scenario.
Earlier full-prompt tail replays did not close; one misrecognized the caller
and did not produce reciprocal farewells. The policy deliberately does not
infer consent from an arbitrary model reply. These are not handset tests.

A later full-prompt tail replay (`goodbye-4d95dde8b486`) waited for the
opening before feeding the recorded farewell. GPT-Live transcribed it as an
acknowledgment rather than a goodbye and continued the conversation, so the
gate correctly stayed open. This illustrates the policy's dependence on the
model's transcript; it does not solve misrecognition or guarantee hangup.


## Full-replay queue failure and recovery

`goodbye-b8d7f3538954` replayed the conversation from the SIP answer boundary
through a clean `07ee67a` candidate. At 90.323 seconds the model's audio burst
crossed the two-second G.711 queue limit and the bridge closed the socket.
This was a separate, reproduced call-disconnection path, before the farewell
could be tested. It is not evidence that a farewell was successfully handled.

The recovery change keeps the two-second bound. An overflowing reply is
explicitly cancelled with boundary `playout_overflow`; local and adapter output
are cleared, and the provider is instructed to stop that explanation. The
connection and caller audio remain live so a subsequent utterance can resume
conversation. The summary counts `playout_overflows` separately from ordinary
interruptions. This deliberately loses the overflowing reply: it is neither a
complete answer nor a successful latency sample. It avoids disconnecting the
entire call or hiding the problem in a growing playback queue.

Regression tests send a 2.2-second burst plus delayed stale audio, observe
cancellation and clear, then send new caller audio and receive fresh output on
the same session. A separate three-second-burst check retains the queue bound.
